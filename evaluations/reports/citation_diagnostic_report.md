## Detailed trace observations

All three cases were policy-isolated in the captured evidence. For AC-001 and AC-002, the schedule reached final rank 1, so the policy evidence was retrieved and survived reranking. The semantic retriever reported zero results without an exception; the cases continued through BM25-only hybrid retrieval. The trace therefore does not support a semantic exception or a reranking loss as the cause of the missing final citations.

The trace records both the raw model output from the client wrapper and the pipeline's `raw_llm_output` before validation. For AC-001 and AC-002, those values contain the expected schedule values and `[Source 1]` labels. The pipeline then records an empty `post_filter_answer`, empty extracted citation labels, no accepted citations, and `suppressed_for_citations`. This sequence establishes the failure mechanism without changing the production behavior.

For AC-003, the ordered Source mapping makes the citation behavior explicit. `Source 1` was the declarations coverage chunk and `Source 2` was the schedule chunk. The parser's exact-label pattern matched the separate `[Source 2]` only; it did not match `Source 1` inside `[Source 1, Source 2]`. This explains partial citation recognition. The trace shows no generation API error and no fallback suppression.

## Limits of the diagnosis

The semantic retrieval result is recorded as zero with `error_type: null` for all three cases. The trace cannot establish why the semantic backend returned zero; it only establishes that no exception was observable at this interface. The report therefore treats the semantic cause as **UNCONFIRMED** and does not infer a Pinecone or embedding failure.

The report does not make a semantic correctness judgment for the generated responses and does not run the 40-case evaluation. Diagnostic traces are local evaluation artifacts and should remain uncommitted.
